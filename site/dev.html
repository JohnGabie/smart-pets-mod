Overview

Smart Pets is a planned Minecraft Java mod: dogs (V1), later cats (V2) and multiplayer (V3) with judgment, genetics, training by cues and a bond with the player. Everything below describes a design. There is no product code and no playable build; the only code is the V0-S0 toolchain spike (a trivial mod with no pet features).

What exists today

  • Consolidated design spec (draft v0.1, pending human approval): docs/spec/SPEC.md; contradictions and gaps found in the design docs: docs/spec/GAP-REVIEW.md.
  • V0 de-risking plan with spikes S0-S11: docs/spec/V0-SPIKES.md.
  • Design history, 26 numbered docs in Portuguese: docs (the spec wins where they disagree).
  • Executable behavior specs: 6 feature files (~67 scenarios), one decision table (R1-R25) and a queue of 18 unspecified situations under specs.
  • Agent roles and the project rules: CLAUDE.md, agents. Evidence journal MODLOG.md (V0-S0 findings) and decision records in docs/adr.

Current stage

Pre-alpha: design and toolchain. The gate in CLAUDE.md says no product code before the human approves both the spec and the plan. Controlled exception: the V0 spikes may write throwaway code to prove tools and risks; each spike ends in an ADR in docs/adr/ and its code is discardable unless the ADR says it graduates. V0-S0 status: PASS-WITH-FALLBACK for what was verified (build, unit tests, headless client GameTest with a screenshot oracle, dev-only debug command), and pending human verification for the live debug bridge with its MCP tools and for the Prism dev instance. Verified commands are listed in CLAUDE.md section 1.

Principles

  • Server authoritative [D]: every rule runs on the (integrated) server, even in singleplayer. The client only captures the microphone and input, renders, and shows UI.
  • Data-driven numbers: every [T] number (chances, times, thresholds, capacities) lives in config/data, never hardcoded. RNG is injected and seeded so tests are deterministic.
  • Decided / proposed / open markers used across the spec: [D] [P] [O] [T] = decided by the human, proposed (needs approval), open question, tuning default.
  • Evidence beats opinion: verify in the game with oracles (screenshot, GameTest, logs); state what was and was not run. Never invent APIs; verify them in real sources for the pinned version.
  • Design invariants (CLAUDE.md section 6), changeable only by the human: no pet teleport; the dog never attacks a player or ally and only attacks a marked target; voice is never the only input; genes never change after birth; permadeath follows world difficulty; age = world day minus birth day.

Structural rules

  • PetRecord is the source of truth [P]: a persistent record (UUID) in world saved data; the entity is a view that may be unloaded while the record survives. Needed for go-home travel, notebook, mourning, lookups and catch-up (spike S4).
  • Versioned persistence [D]: schema version plus migration on every persisted structure; unknown fields are preserved.
  • Prefer loader API events over mixins; each mixin needs a written justification and a GameTest.
  • Multiplayer-ready message design: every command carries a speaker id; bond is stored as a map keyed by player id.
  • Compatibility: other mods that replace wolves are incompatible by design; to be documented.

Entity strategy [P]

Use dedicated custom entity types (dog, later cat). Do not subclass or mixin the vanilla Wolf. Reasons given in the spec:

  • the design removes teleport-follow;
  • taming, breeding and AI are changed wholesale;
  • it avoids conflicts with the vanilla class and with other mods.

Vanilla wolves in the world are replaced at spawn by the wild dog through biome spawn modification. This must be confirmed in spikes S3 and S6 (custom entity, model and animation; AI core). Related open decision: docs/spec/SPEC.md section 24 item 3.

Where state lives

  • Genes: on the PetRecord, fixed at birth.
  • Needs, bond, mastery: core state persisted on the record, with catch-up on load (capped).
  • Coat: stored as genes plus seed; textures composed client-side deterministically.
  • Block entities for bed, bowl and den carry ownership data (spike S4).

Wild generation-1 dogs get randomly generated traits, not under player control [D]. Coat uses alleles with dominance and hidden carriers; other traits are continuous [D].

Needs and state vector

  • Needs: satiety, energy (% of capacity, may overflow), companionship, health, weight/body condition, comfort (cold/wet), training fatigue/stress, play need.
  • Mood is derived from needs plus recent events; it drives animations, sounds and obedience.
  • Weight: lean, ideal, plump, fat, obese. Affects speed, stamina, jump and snoring; reversible; never kills [D]. The appetite gene shifts the curve.
  • Energy overflow up to about 130% [T] triggers frenzy (zoomies); below 0% the dog collapses and sleeps, no damage [D].
  • Bond: per person, 0-100%, daily gain caps [P], slow decay on long absence down to a floor [T]. Bond is how willingly, skill is what it can do [D].

Inheritance rule

Child trait = mean(parents) + noise [D] for the rule, [T] for the values:

ShareOutcome
~80%normal puppy
~15%"rough diamond": 1-2 traits notably above both parents
~1-2%"genius": several high traits, raised training ceiling, with a built-in cost (e.g. high clinginess or energy)
  • Regression to the mean: a genius's children mostly return to average; the ceiling bonus is rarely inherited.
  • Some chance a puppy comes out below its parents. Orphans get a small bias in these odds.
  • Wildness = parents' mean minus a per-generation drop.
  • Reproduction follows vanilla (feed two adults, love mode), no estrus or pregnancy; litter 3-5, about 20 days between litters per mother [T].

Time and age model

  • Clock = the world day counter (the "Day N" of F3 / /time query day), not real time [D]. Exact source and edge cases (sleep, /time set, daylight cycle off) are spike S11.
  • age_days = max(previous_age_days, current_day - birth_day): monotonic, never decreases when time is set back [P]. Scenario: born day 10, world day 40 gives 30 days; set back to 20 still 30.
  • Mod year = 10 world days [T][O]; lifespan 8-16 mod years = 80-160 days.
  • Catch-up on load: needs, loneliness, rust and aging use elapsed days with caps; long absences are never punished like neglect [D].

Behavior and AI

From docs/spec/SPEC.md sections 8, 10, 11 and specs/matrix/cue-handling.md.

The four layers

#LayerWhat it does
0Reflex (always wins)Danger avoidance; drops a target that is an ally, player or pet; flees lethal threats.
1CommandThe dog evaluates the order. Refusal is visible (head tilt, ignoring), never silent.
2InitiativeAsk for food, warn, defend owner, ambush, bring gifts, play. Weights are learned: reward raises, ignoring lowers, the "no" cue lowers. Vices are behaviors whose weight training reduces.
3RoutineSleep in bed or den, guard home, wait at the door.

Utility scoring and commitment

  • Utility scoring across candidate behaviors with a commitment time so the dog does not oscillate; it thinks every N ticks, not every tick [T].
  • Postures: free, near, guard. The work harness is a focus mode that also suppresses frenzy and mischief.
  • Idle animations are sampled from state, not random.
  • The engine lives in core; the platform adapter feeds it senses and executes its choices (spike S6, 20 dogs at once).

Danger model (layer 0)

Data-driven table. It is the foundation that makes permadeath fair [D].

AvoidNever target
lava, fire, magma, cactus, void edge, deep fall, deep water drowning, powder snow, sweet berries (as relevant), a creeper about to explode (retreat), overwhelming mob groups, explosions, wither effectsplayer, owned/allied pets, villagers unless configured

Also: disengage when ordered; never keep attacking to the death. Whether vanilla Wolf hostilities (e.g. toward skeletons) are kept is [O].

Obedience inputs

Willingness = f(association strength, bond with the speaker, mood, loyalty, fatigue) [P]. Other effects in the spec: overtraining shows warning signs (yawn, sniff ground, scratch, look away) then nervous or disinterested; wild dogs obey no cue and use a trust ladder only (R23).

Cue abstraction [P]

A cue is an abstract token that triggers a command: a voice template, chat text, or a key/UI button. Training teaches a cue-to-command association, so any language or sound works and non-voice players train with chat or keys. Voice, key and chat become the same internal command (rule R22).

  • Name first, command second: the dog's name cue gains attention, then a command must follow within a short window (about 3 s [P][T]; scenarios use 4 s to expire). A name alone never triggers a command.
  • Two names: a text name (name tag/UI) and a learned name cue.
  • Cue consistency is required (similar sound or same text); a different cue each time means no learning.
  • Reps to learn: simple 3-6, medium 8-15, advanced 20+, scaled by intelligence, stage, bond and mood [T].
  • Mastery: 5 levels per skill; rust reduces progress first and never below "learned". Soft prerequisites with three hard locks besides Name: Release/No needs Fetch or Attack; Flank/Ambush needs Attack; Go-home needs Come.
  • Pet selection with several dogs: by name cue, crosshair or radial list [P]; mark target by looking at an entity plus cue/key.

Voice

Highest-risk item of V0. Sources: docs/spec/V0-SPIKES.md (S1), docs/spec/SPEC.md sections 8, 19, 22, docs/08-taming-voice.md.

Approach

  • Learn arbitrary sounds or words, in any language, locally, inside the game. The dog learns a cue; nothing is a fixed vocabulary.
  • Feature extraction (e.g. MFCC) plus alignment-based matching (e.g. DTW), or a small embedding model. Pure Java in core, offline-testable with WAV fixtures.
  • A strictness parameter tied to the dog's intelligence (intelligence governs cue generalization in the genome; UNSPECIFIED #6 covers recordings and other voices).
  • Push-to-talk by default; continuous listening optional; if S1 passes, voice is enabled by default in config [D]. The dog responds only within its hearing range; a whistle extends it.
  • Voice ships in V1 if S1 passes, otherwise V1.5. Voice is never the only input: every voice feature has a key/chat/UI path.

Spike S1 acceptance criteria

  • Fixtures: author plus one other speaker, at least two languages, ambient noise, speech that is not a cue.
  • At least 3 cues with 10 or more recordings each.
  • Recall of at least 90% at no more than 2% false accepts on at least 30 minutes of non-cue speech and noise.
  • At most 500 ms from key release to command; negligible frame impact; capture off the main thread.
  • Works on the author's Linux audio stack. Needs the human to record samples and judge feel.

Fallback ladder

  1. Tuned matcher
  2. Pretrained small keyword-spotting model with user-trained words
  3. Text and key cues only (voice becomes an optional extra)

Privacy [P]

  • The microphone is opt-in; processing is local; no network.
  • Only the features of learned cues are stored per dog; raw audio is not saved.
  • Debug tools exist only in disposable dev instances.

Plain-text, executable specifications designed in docs/spec/BEHAVIOR-SPECS.md. The same text is spec, acceptance criteria and regression suite, and its job is to find the situations nobody thought of.

The cue-handling matrix

  • Dimensions: input, look target, dog state, hearing, bond, learned, dogs in range, speaker, input channel.
  • Rules R1-R25, first match wins; R25 is "anything else" which yields UNSPECIFIED and the safe default (ignore + head_tilt, never harm, never crash).
  • Pairwise coverage for the first pass; full expansion for the safety-critical slice (target in player, ally pet or villager, with any input).
  • Examples: R1 out of hearing range gives no reaction; R6 name only gains attention; R10 never attacks a player or ally pet; R22 voice, chat and key behave identically.
  • Source: specs/matrix/cue-handling.md

The UNSPECIFIED queue

specs/UNSPECIFIED.md holds 18 situations found while writing the specs, each with a safe default now, a proposal and a decision status (3 decided, 15 pending at the time of writing). Flow: QA runs and fuzzing collect UNSPECIFIED_SITUATION journal events; the architect triages them into the queue; the human decides; resolved items become @decided scenarios. Coverage reported per PR: scenarios by tag, matrix cells covered/unspecified, property seeds run, journal events never asserted, unspecified situations observed.

Version control and PR flow

  1. One branch per task, named type/short (e.g. feat/energy); never commit to the main branch directly.
  2. Small commits, clear messages; no force-push, no history rewrite, no deleting other people's branches.
  3. The executor opens a small PR: task, what changed, how it was verified, what was not verified.
  4. Reviewer verdict, then QA report, then the human merges (default). The merge needs Reviewer OK plus QA OK.
  • Labels: if everyone uses the same GitHub account, formal approval may be impossible, so the verdict is carried by labels and a verdict comment. Label set defined in agents/agent-version-control.md: needs-qa, qa-passed, approved-by-reviewer, changes-requested, blocked, v0-spike, v1, v2, v3, design-decision.
  • Local protections: GitHub's free plan has no branch protection on private repos, so run git config core.hooksPath scripts/dev/git-hooks once per clone (blocks direct push to main and force-push). Helper scripts: scripts/dev/backup-repo.sh, scripts/dev/branch-health.sh, scripts/qa/docs-freshness.sh.
  • Parallel executors use separate worktrees/branches and distinct file owners; two executors never edit the same file.
  • One PR, one task, one goal.

Rules summary

Do

  • Pin version, loader and dependencies before any code.
  • Read the project and follow its conventions.
  • Compile after each change.
  • Verify APIs in real sources for the pinned version.
  • Write behavior specs and tests first; test pure logic without Minecraft.
  • One small feature at a time.
  • Write a contract where state crosses a boundary.
  • Server decides, client draws.
  • Verify in the game with oracles; log in MODLOG.md.
  • Report real status, including what was not run.
  • Version every persistent schema.

Don't

  • Invent APIs, classes or commands.
  • Copy code, models, textures or sounds without a permitting license (all rights reserved = forbidden).
  • Put game files or decompiled code in the repo.
  • Use debug tools outside a disposable dev instance.
  • Touch real saves without a backup; kill processes by name.
  • Store keys, tokens or personal data.
  • Mix tasks in one PR; approve or merge your own work.
  • Use AI-generated images on the mod page, icon or gallery.
  • Hide failures, skip tests or mark done without evidence.

Definition of done

Build passes + the brief's tests pass + acceptance criteria verified with evidence + no invariant violated + no unverified API + asset licenses and origin clean + MODLOG updated + Reviewer OK + QA OK.
